# Plan v0.1.26 — Serveur v2 : reconnaissance de pages complètes (MinerU)

> **Pour les agents d'exécution :** sous-skill REQUIS : superpowers:executing-plans (méthode choisie par Arthur, « comme pour les 24 versions précédentes »). Les étapes utilisent des cases à cocher (`- [ ]`).

**Objectif :** le serveur OCR personnel gagne l'endpoint `/page` qui reconnaît une page complète (texte, formules, titres, tableaux, images) par MinerU, un bouton « Tester la reconnaissance » dans l'application envoie une page et affiche un résumé lisible, et un script comparatif mesure les deux niveaux de MinerU sur des pages réelles.

**Architecture :** contrat v2 AJOUTÉ au serveur v0.1.23/25 sans toucher au chemin `/ocr` (bouton ƒ LaTeX inchangé) ; MinerU 4.x appelé en paresseux derrière le verrou d'exécution, mode banc étendu (page factice complète sans moteur) pour valider toute la chaîne avant installation ; l'app rend la page courante en JPEG ~200 points par pouce et affiche le décompte des blocs.

**Pile :** Python 3.12 (bibliothèque standard côté serveur, MinerU en paresseux), py -3.12 sous Windows ; JavaScript maison côté app (pdf.js pour le rendu), fonctions pures dans engine/ testées par node --test.

**Spécification :** docs/plans/2026-11-22-document-vivant-design.md (le présent plan plaide depuis cette conception ; en cas de conflit, la conception l'emporte), complément vérifié le 22/11 : MinerU publié en est à la version 4.2.3 (« mineru[core] » n'existe plus ; l'interface est `from mineru.parser import parse`, niveaux flash/basic/standard/advanced ; le niveau « basic » = petits modèles sans VLM, « standard » = petits modèles + VLM — l'équivalent pipeline/VLM du cadrage ; le VLM Windows passe par llama.cpp inclus au paquet de base).

## Contraintes globales

- Python 3.12 EXACTEMENT sous Windows (`py -3.12`) : rapid-latex-ocr refuse >= 3.13, mineru 4.x exige >= 3.11.
- Le chemin `/ocr` et le bouton ƒ LaTeX restent fonctionnels À L'IDENTIQUE (anti-objectif n° 3 de la conception).
- Jeton v0.1.25 : `/page` vérifie l'autorisation AVANT de lire le corps, comme `/ocr` ; GET de diagnostic ouvert.
- Verrou d'exécution UNE requête à la fois, PARTAGÉ entre `/ocr` et `/page` (les deux moteurs ne tiennent pas ensemble sur 8 Go de VRAM ; la conception dit « verrou d'exécution une requête à la fois »).
- Erreurs serveur en français, mesurées dans le JSON `{"erreur": "…"}` ; l'app affiche le détail du serveur.
- Délai applicatif côté app : 10 minutes par page (`AbortSignal.timeout(600000)`) ; le serveur n'impose pas de délai.
- Taille du corps acceptée : inchangée (64 Mo maximal) ; images PNG ou JPEG.
- L'app ne reçoit JAMAIS les pixels reconnus : le type « image » ne porte que sa bbox (l'app recadre localement).
- Banc d'essai uniquement en bibliothèque standard : `test_serveur.py` ne doit PAS importer mineru (la CI n'installe pas mineru).
- Conventions app : fonctions pures dans engine/ + tests dans test/ ; messages français ; aucun secret n'est jamais rappelé à l'écran.
- Licences : mineru est AGPL-3.0 (modèles YOLO), compatible avec le dépôt AGPL-3.0 ; le LISEZMOI le documente.

## Revue ciblée (ce qu'aucun test d'étape ne couvre et qui mordra le premier)

1. URL du serveur enregistrée SANS suffixe `/ocr` (ex. funnelle racine) : `pageUrlDepuisServeurUrl` doit quand même produire une URL `/page` — test en T3.
2. Schéma MinerU qui dérive à l'installation réelle (la 4.x n'est pas installable ici) : le transformateur ne doit JAMAIS lever ; types inconnus ignorés, bbox absents ignorés — tests en T2.
3. Page reconnue VIDE (aucun bloc exploitable) : réponse 200 avec `blocs: []`, résumé lisible « aucun bloc » — test en T2.
4. Image reçue sans dimensions lisibles (en-têtes PNG/JPEG atypiques) : `lireTailleImage` ne doit pas lever — test en T1.
5. Requête `/page` reçue pendant qu'un `/ocr` tourne : le verrou partagé fait attendre, pas échouer — couvert par le code du verrou (aucun test multi-thread au banc, départage impossible sans mineru ; consigné au registre).
